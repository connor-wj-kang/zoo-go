# 5km 地理围栏与派单对比

## 1. 业务边界

当前实现解决的是“附近任务可见、可报价”和“运营侧算法对比”两件事：

1. 主人在发布任务时选择真实地图位置，后端保存经纬度。
2. 学生进入任务大厅时上报当前位置，只能看到有效直线距离不超过 5km 的竞价任务。
3. 学生提交报价时，后端再次计算距离，防止绕过前端展示规则。
4. 管理后台展示贪心算法与 KM（匈牙利算法）的只读批量匹配对比。

当前不会自动把任务派给某个学生。真实成交仍由主人查看报价后选人，并继续经过唯一订单、10 分钟待支付、微信支付和订单状态机。算法结果不会直接修改任务、报价或订单。

## 2. 坐标与硬限制

- 主人位置来自 `wx.chooseLocation`，学生位置来自 `wx.getLocation({type: "gcj02"})`，两端使用同一套 GCJ-02 坐标。
- 距离使用 Haversine 球面直线距离，地球半径取 `6371.0088km`。
- 平台最大派单半径为 5km。小程序固定上报 5km；后端允许 1–5km 的接单半径，异常或缺失时回退到 5km。
- `GET /v1/student/tasks/available` 先校验学生已上报定位，再逐条过滤没有坐标或超出范围的任务。
- `GET /v1/tasks/{id}?role=student` 对尚未报价的竞价任务执行同样的距离校验，避免通过任务 ID 绕过大厅。
- `POST /v1/tasks/{id}/bids` 使用数据库中的任务坐标与学生坐标重新校验，超出范围返回 `403`。
- 经纬度不会通过学生端 JSON 返回。成交前学生只看到小区与 `distanceKm`；付款后才按订单权限开放详细门牌。

历史上没有经纬度的任务不会进入附近任务大厅。重新发布任务或重新选择服务位置后才会参与 5km 匹配。

## 3. 候选数据

管理端对比接口只读取当前可用数据：

- 任务：状态为 `BIDDING`、报价截止时间未到、经纬度有效。
- 学生：账号正常、学籍认证有效、已上报过有效坐标。
- 候选边：任务与学生之间的 Haversine 距离不超过 5km。
- 默认最多取 50 个任务、100 个候选学生，接口可通过 `limit=1..100` 调整任务上限。

接口只返回任务 ID、小区、学生 ID/姓名、距离和得分，不返回精确经纬度。

## 4. 综合得分

每条任务—学生候选边的得分为 0–100 分：

```text
综合分 = 距离分 + 评分分 + 经验分 + 基础信用分

距离分 = 50 × (1 - 直线距离 / 5km)
评分分 = 12.5 + 12.5 × (学生评分 / 5)
经验分 = 15 × min(完成单数, 20) / 20
基础信用分 = 10
```

学生评分限制在 0–5，完成单数限制在 0–20。距离越近得分越高；距离相同时，评分和完成经验更高的学生优先。该得分不含报价金额，价格仍由主人结合报价决定。

## 5. 贪心算法

贪心算法先对所有候选边按综合得分从高到低排序，得分相同则优先距离更近，再按任务 ID 和学生 ID 稳定排序。随后依次选择当前最高分边；如果任务或学生已经被占用，就跳过该边。

特点是实现简单、响应快，但可能因为先占用了某个学生，导致后续任务失去更合适的全局组合，结果只是局部最优。

## 6. KM / 匈牙利算法

KM 对比使用匈牙利算法求二分图一对一最小成本分配。实现把“综合得分”转换为成本，并给每条真实匹配增加固定数量奖励，因此优化顺序是：

1. 先最大化成功匹配数量。
2. 在匹配数量相同时，最大化综合得分总和。

虚拟行或虚拟列表示“本批次不匹配”，但空匹配成本高于任何真实候选边；候选学生不足时，算法不会为了追求零成本而把真实可匹配边全部留空。复杂度为 `O(n³)`，适合当前管理端小批量预演，不放在学生请求链路中。

## 7. 查看方式

启动 API 后，使用管理后台登录：

```text
http://127.0.0.1:8080/admin/
```

进入“派单对比”，页面会展示：

- 待派任务、可用学生和 5km 候选边数量。
- KM 与贪心的匹配数、总得分、总距离。
- 两种算法逐条任务—学生分配明细。
- KM 相对贪心的总得分差。

管理员接口为：

```http
GET /v1/admin/dispatch/compare?limit=50
X-Admin-Token: <ADMIN_TOKEN>
```

接口返回中 `readOnly` 固定为 `true`。

## 8. 升级为真实自动派单

若要允许系统自动成交，不能直接复用当前只读结果。至少需要补充：

- 派单批次快照和版本号，避免预览后任务/学生状态变化。
- 带超时的任务唯一领取，最终仍由数据库唯一索引保证一单只能有一个履约学生。
- 领取事务内复核学籍有效期、学生时段冲突、报价资格、位置时效和任务状态。
- 超时释放、候选人通知、失败重试、人工兜底和可审计回滚。
- 如使用 Redis，可做短暂分布式锁或通知队列，但锁不能替代数据库事务和唯一约束；最终一致性仍以 SQLite/关系库状态为准。
- 自动派单后的支付、退款、取消和重新竞价继续走现有订单状态机，不得另开绕过路径。

在这些条件完成前，KM 结果仅作为运营参考。
